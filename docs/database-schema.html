HERS Events — Database Schema (public)

Generated from app/db/schema.ts + relations.ts. Arrows point from a foreign-key column to the primary key it references. The neon_auth schema is on page 2; query notes on page 3.

neon_auth schema (managed by Neon Auth)

A separate Postgres schema provisioned by Neon Auth. It is not linked to the public tables — the app's FKs all point at public.user (text ids), not neon_auth.user (uuid ids).

Notes for writing queries & server functions

Things in the schema that will shape your code — cascade rules, uniqueness, join tables and the Drizzle relation names you can use in db.query.*.findMany({ with: … }).

The two hubs

  • events owns almost everything: enrollments, check_in_points, subcommittees, announcements, tracks, sessions_agenda, speakers, event_links. Deleting an event cascades to all of them (and onward to check_ins, subcommittee_members, announcement_reads, session_speakers).
  • user is the actor: who created an event, sent an announcement, checked someone in, invited staff, changed a setting, or wrote an activity_log row.

Deleting a user will fail if…

These FKs to user.id have no ON DELETE rule (Postgres default = NO ACTION), so the delete is rejected while any row still points at the user:

  • events.created_by
  • announcements.sent_by
  • check_ins.checked_in_by
  • staff_invites.invited_by
  • enrollments.user_id (nullable)
  • settings.updated_by (nullable)
  • activity_log.actor_id (nullable)

Only account, session and announcement_reads cascade. Plan to reassign / null these out, or ban instead of delete.

Enrollment lifecycle

  • An enrollment is created from an email first: invited_email is required, user_id is nullable and filled in when the attendee signs up.
  • status enum: invited → active → revoked (default invited).
  • Unique on (event_id, invited_email) — use onConflictDoNothing/DoUpdate for bulk invites.
  • Access: events.access_expiry is the event-wide cutoff; enrollments.individual_expiry can override per person.
  • events.access_key is unique — a natural lookup key for join links.

Check-ins

  • Each event has one or more check_in_points (default label "Arrival", optional date for multi-day events).
  • A check-in links a point + an enrollment (not a user) + the staff user who scanned it.
  • Unique on (point_id, enrollment_id) → one check-in per person per point. Duplicate scans will throw unless you handle the conflict.

Join tables (composite PKs, no id column)

  • announcement_reads (announcement_id, user_id) + read_at
  • session_speakers (session_id, speaker_id) + sort_order
  • subcommittee_members (subcommittee_id, enrollment_id)

Insert with onConflictDoNothing() to make "mark read" / "add member" idempotent.

Agenda

  • sessions_agenda = a talk/slot (the table name avoids clashing with the auth session table). Indexed on (event_id, starts_at) — order by starts_at.
  • track_id is optional and set null when a track is deleted.
  • Speakers belong to an event and attach to sessions through session_speakers.

Drizzle relation names (relations.ts)

events:   enrollments, checkInPoints, subcommittees,
          announcements, tracksEventId, sessionsAgenda,
          speakers, eventLinks, activityLogs,
          user (= creator)
enrollments: event, user, checkIns,
          subcommitteeMembers, subcommittees (via join)
sessionsAgenda: event, track, sessionSpeakers,
          speakers (via join)
announcements: event, user (= sender),
          announcementReads, users (readers, via join)
checkIns: checkInPoint, enrollment, user (= staff)
user:     enrollments, eventsCreatedBy,
          announcementsSentBy, checkIns, staffInvites, …

Note: an event's tracks are tracksEventId, not tracks (tracksViaSessionsAgenda goes through the agenda instead).

db.query.events.findFirst({
  where: { id },
  with: {
    sessionsAgenda: { with: { speakers: true, track: true } },
    enrollments: { with: { checkIns: true } },
  },
})

Auth / admin tables

  • user, account, session, verification are the Better Auth tables (text ids). user.role, banned, ban_* come from the admin plugin; password_cleared is app-specific.
  • staff_invites: unique token; an invite is open while used_at and cancelled_at are both null.
  • settings: key/value store, key is the PK — upsert on it.
  • activity_log.event_id is set null when the event is deleted, so the log survives.
